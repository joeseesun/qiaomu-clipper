# 播放器中文字幕：时间与语义对齐调研

日期：2026-10-13。核对对象为固定测试入口 CURRENT.json 指向的 1.18.1，提交 fc34bdd，含播放器字幕未提交增量。用户确认问题同时涉及显示时机和翻译表达。以下是源码诊断与改进建议，尚未替换测试包。

## 已确认的问题

- `player-captions.ts` 的 current() 用 findIndex 返回第一条覆盖当前时间的字幕，没有先处理重叠。直接执行实际 CaptionQueue 代码复现：前一条 [0,8)、后一条 [4,6)，在第 5 秒仍选前一条。对同一说话流的滚动更新，需要识别更新关系和截断旧字幕；双人同时说话需另外保留，不能一律删除重叠。
- `youtube-captions.ts` 把 JSON3 的 segs 文本合成一条，未使用 tOffsetMs、aAppend 等滚动字幕信息。平台事件边界不一定是完整表达边界。
- B 站桥接每 400 ms 报时。当前字幕只在新报时到达时切换，不插值；理想 2 倍速条件下一个报时间隔已经对应 0.8 秒媒体时间。这是理论更新粒度，尚未测量用户视频的实际误差。
- 翻译以原始片段 ID 为单位，上下各一条作为上下文；固定最多五条串行批量请求，等待整批 JSON 返回才应用。启用时尚无预译缓冲，短句可能在译文准备好之前结束。已结束的译文不会延后强行显示，但用户会看到缺失或迟出现。
- 旧阅读文稿只剩段落时间戳时，回退最多显示六秒。复现长段从第 10 秒到第 30 秒，实际 cue 被回退为 [10,16)，无法据此还原逐句声音位置。
- 生成字幕链路的 native/asr.py resplit 和 native/asr_cloud.py cues_from 在只有长文本、没有细粒度时间时按字数分摊时长；部分识别器虽产生词时间，落盘清理只保留段的 start/end/text。字数比例不代表真实停顿和语速。

这些问题可以解释用户描述，但尚未用具体问题视频排除原字幕错字、翻译模型误译或不同音轨。之前的播放器测试主要使用不重叠的干净 cue 和模拟译文，没有证明滚动字幕或生成字幕的真实表达对齐质量。

## 对照项目与规范

- [Read Frog 滚动字幕解析源码](https://github.com/mengxi-ream/read-frog/blob/main/src/utils/subtitles/fetchers/youtube/parser/scrolling-asr-parser.ts)：利用词偏移、滚动事件和句尾构造字幕，处理前后重叠。[官方显示文档](https://www.readfrog.app/en/docs/video-subtitles) 支持中文单语和双语，明确 AI 重分句可能增加延迟、降低时间精度。借鉴解析、缓存与调度，不让 LLM 自由生成时间戳。
- [VideoLingo 对齐与拆分](https://github.com/Huanshere/VideoLingo/blob/main/core/_5_split_sub.py)、[时间恢复](https://github.com/Huanshere/VideoLingo/blob/main/core/_6_gen_sub.py)：源文和译文一起拆分，数量必须对应；用源词的位置恢复首尾时间。借鉴语义翻译与显示分段分离，不把整个离线视频处理流水线装进浏览器播放器。
- [WhisperX](https://github.com/m-bain/whisperX)：先识别原文，再与原音频做强制对齐，得到词时间；数字、部分语言与重叠讲话仍有限制。只在原时间缺失或明显不可信且能够取得音频时使用，不能直接拿中文译文与外语发音强制对齐。
- [stable-ts](https://github.com/jianfch/stable-ts#regrouping-words)：按标点、静音间隔、长度和时长重新组织已有词时间。借鉴保留时间证据的规则分句，不把纯文本分句当成精准对齐。
- [Netflix 简体中文字幕规范](https://partnerhelp.netflixstudios.com/hc/en-us/articles/215986007-Chinese-Simplified-Timed-Text-Style-Guide)：普通中文字幕每行 16 字、最多两行，成人读速上限 9 字/秒。这是影视交付规范，可作为可读性参考；学习播放器应按视口、倍速和内容调优，不机械删去信息凑长度。
- [浏览器视频帧回调](https://web.dev/articles/requestvideoframecallback-rvfc) 提供呈现帧的 mediaTime；[YouTube IFrame API](https://developers.google.com/youtube/iframe_api_reference) 提供播放时间、速度和播放/暂停/缓冲状态。跨域 iframe 不能直接访问内部 video，需通过播放器适配器获取证据。

## 建议的下一版

流程：保留源字幕/源词时间 → 清理滚动更新和重复 → 构造完整语义单元 → 带上下文忠实翻译 → 对应到短字幕 → 预译缓存 → 按播放器时钟显示。

1. 时间与含义分开负责。翻译模型只输出文字及源片段/源词的引用范围，时间戳由程序查原轨计算。校验范围顺序、覆盖、遗漏和重复；语义对齐失败保留原片段，不用字数比例冒充准确时间。
2. 先理解整句，再拆成适合播放的短语。翻译上下文包含完整句子和附近段落/术语，避免半句误解。源文与中文按含义共同分段；只持有 cue 时间时，不凭空切出词级时间。只有文本时标明时间为估计，精准模式需要源词时间或重新音频对齐。
3. 预译与显示独立。启用时优先准备当前短语和后续片段；缓冲窗口随模型响应时长与播放速度调整。拖动立即换优先级；迟到译文仅缓存，绝不挤占下一句。保留单语/双语下各自正确的等待状态。
4. 播放器统一时钟。原生 video 优先使用帧回调并补暂停/seek 事件；iframe 用最新时间、速度和单调时钟短时插值，遇暂停、缓冲、seek 或失去新报时立即重置/冻结。报时样本持续校准，不能在卡顿时盲目推进。
5. 显示以中文短句为主，可切双语对照。中文单语最多两行；自然语义断行，固定位置，保持完整字幕稳定，避免边收到模型 token 边改写已显示内容。阅读文稿与播放器共享同一翻译结果和源 ID，避免同一句两个版本。无法同时满足忠实和读速时提供慢放/暂停阅读，而非悄悄删减。

第一阶段先修滚动/重叠、时钟、提前缓冲和翻译上下文；不增加识别依赖。第二阶段提升生成字幕的原词时间保留与可选音频对齐，需要单独验证助手运行时与模型，不作为所有视频的强制步骤。

## 验收

使用真实格式 fixture 验证滚动 JSON3、词偏移、重叠、长停顿、缺结束时间、旧段落缓存；实际播放器验证 1×/2×、暂停、缓冲、拖动和慢模型。区分原轨时间误差与播放器显示误差。中英含义人工抽查否定、数字、人名、代词指代、长句和跨片段语序，不以 JSON 格式通过作为翻译准确通过。需要真实 YouTube/B 站各一段以及一段生成字幕录播验收。
