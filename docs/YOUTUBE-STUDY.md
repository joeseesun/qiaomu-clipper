# YouTube 沉浸学习（1.8.0）

YouTube 视频页的 `aaa` 快捷键进入剪藏草稿的阅读预览。旧版将正文经过 Markdown 转换和 HTML 清理后渲染，播放器 iframe 与字幕结构信息丢失，结果只有视频说明和文稿。

新版在渲染后的文章中根据原始 YouTube URL 恢复播放器，仅接受 YouTube 官方域名及合法视频 ID；恢复 Markdown 字幕的时间戳、字幕行样式与播放跳转元数据。播放器位于文稿上方，视频说明保留在文稿之后。Chrome 播放器在 Referer 规则安装后重新加载，避免从 0:00 打开的草稿先发出缺少 Referer 的嵌入请求。

文稿工具栏支持复制带时间戳的字幕、下载 UTF-8 TXT，以及打开基于字幕的 AI 对话。字幕导出排除视频描述、章节标题和阅读器按钮。AI 沿用现有模型设置与对话历史；草稿预览使用字幕作为上下文。原页沉浸模式的 AI 请求通过扩展后台流式转发，停止对话会断开连接并取消后台请求。没有取得字幕时显示状态并禁用文稿操作，可先打开 YouTube 原页转写面板再重试。

## 验证

- 回归测试覆盖 Markdown 播放器恢复、合法域名/ID、字幕时间戳还原、复制/下载与 AI 上下文一致性、无字幕状态、避免重复播放器和工具栏、后台流式转发与取消。
- 类型检查与 Chrome/Firefox/Safari 构建作为发布检查。
- Chrome 已安装扩展已重新加载到 1.8.0；`aaa` 打开草稿预览的链路已观察到。
- 完整的修复后播放、跳转、导出和 AI 实际响应验收仍待完成：自动浏览器策略禁止直接导航扩展内部 URL，已请用户从视频页打开新版阅读预览。此记录不将构建或 iframe 恢复测试视为实际播放成功。

## 1.8.1：播放器优先、字幕异步加载

旧快捷键先打开剪藏弹窗，等完整提取后消费待执行阅读指令；该指令在 15 秒后过期，字幕加载较慢会停留在弹窗。新版在 YouTube 视频页按 aaa 时，直接创建学习阅读页；普通网页和编辑/剪藏快捷键沿用原流程。

学习页先渲染播放器，然后读取原视频页当前 DOM 并异步提取字幕；原页仍在加载字幕时，不影响播放。每次提取最多等待 20 秒，超时或无字幕显示可见状态和重试按钮。重试重新读取源页面，不刷新播放器。文稿成功后附加时间轴与 AI/导出工具，最后启用剪藏按钮，避免保存加载占位文案。实际浏览器加载与播放验收仍待用户确认；自动浏览器策略禁止访问扩展内部页面。

## 字幕为什么常常读不到，现在怎么取（2026-10-03）

**原因**。官方 clipper 在 YouTube 页面里直接运行 Defuddle：用页面自己的 `fetch`（带 YouTube 的 cookie 和来源），读取页面已有的数据，不行再点开页面上的转写面板读取。学习页原来是在扩展页里拿一份静态 HTML，再通过后台代理去抓字幕文件：请求没有 YouTube 的会话，也没有页面上的播放器令牌，静态副本里还打不开转写面板，所以 YouTube 返回空内容时就没有任何兜底。

**现在**。三条路同时/依次取，谁先拿到字幕用谁：

1. **原页提取**（新）：后台让视频所在标签页里的内容脚本执行与官方 clipper 相同的 `getPageContent`（页面 `fetch` + Defuddle 的面板兜底）。
2. **原页转写面板**（新，兜底）：第 1 条仍没有字幕时，在原页点开「转写文稿」，直接读取 YouTube 自己渲染出的字幕行（它是页面用你的登录会话请求的，不受字幕文件限制影响）。
3. **静态副本 + 后台代理**（原有）：原页不可用（标签被关）时仍能工作。

三条都失败才提示「暂未获取到字幕」，此时按提示在原页打开转写文稿再重试。B 站同样先走原页提取，登录会话天然生效。

**限制**。原页提取会在你的视频页里点开转写面板（与官方 clipper 的兜底行为一致）；YouTube 改版转写面板的结构时，第 2 条需要跟着更新（解析逻辑与「复制 / 下载」按钮共用）。本机无法登录真实账号验证，只用单元测试和结构探查核对，未在真实视频上跑通。

### 为什么要重试好几次（已修）

重试一两次才成功，是因为第一次其实在「预热」页面，而不是真的失败：

1. 按 `aaa` 后立刻开始取，此时 YouTube 的描述区和转写面板还没渲染完，找不到「显示转写文稿」按钮，兜底直接放弃；
2. 字幕文件请求要等 4 秒级的超时才会失败，两三个请求叠加后撞上总时限，第一次整体超时；
3. 超时时原页里的提取并没有停，它顺手把转写面板点开了——所以第二次读到的是现成的字幕行，一下就成功。

现在的顺序：

- **先开面板再提取**：后台先让原页等待并点开转写面板（按钮还没出现就等，不重复点击已展开的面板以免关掉；面板停在「章节」页会自动切到「转写文稿」），字幕行渲染出来后再执行完整提取，此时 Defuddle 直接读页面上的字幕，不再靠网络和超时。
- **自动补一次**：第一次没拿到时，静默等 1.5 秒再试一次，才显示「重试」按钮。
- **总时限放宽**：20 秒→35 秒（原页提取最长 28 秒）。

### 入口卡片与字幕预取

不再等 YouTube 懒加载转写面板：

- **入口卡片**：视频页右侧栏最上方常驻「乔木 · 沉浸学习」卡片（沉浸学习 / 复制 / 下载），不依赖转写面板，页面一加载就在；设置里「YouTube 转写文稿按钮」同时控制它和面板里的三枚按钮。
- **预取**：页面空闲后（以及站内切到下一个视频后）在 YouTube 标签页里请求一次 `/youtubei/v1/next`，取出 `getTranscriptEndpoint`，再调 `get_transcript` 拿字幕行并缓存；按 `aaa` 或点卡片时直接用缓存，学习页只需要从页面副本读标题和简介（不走网络），不再等任何超时。
- **兜底不变**：预取没有结果时，依次走「点开转写面板读取」和原来的整页提取；转写条会显示「没有读到字幕」和「重试」。
- **已知限制**：在未登录的会话里实测 `get_transcript` 返回 400（Precondition check failed，YouTube 要求播放器令牌）。预取连续两次被拒绝后，本页不再重复请求，直接走面板兜底；已登录账号下是否可用本机无法验证。解析函数、请求顺序和降级逻辑有单元测试。

### 自动展开转写面板

YouTube 默认不展开右侧的转写文稿面板；以前要点一下插件图标，提取器兜底时顺手点开它，面板里的按钮才出现。现在视频页空闲后会**自动展开一次**（设置里「自动展开 YouTube 转写文稿」，默认开启）：

- 每个视频只展开一次；你关掉之后这个视频不再自动展开，切到下一个视频才会再来一次。
- 面板里渲染出的字幕行同时作为「字幕已就绪」的来源，复制、下载和学习模式直接使用，不再等预取接口（未登录时它会被 YouTube 拒绝）。
- 页面结构里还没有「显示转写文稿」入口时不做任何事，等页面渲染到之后再试，不会反复点击。

### 转写面板里的按钮：位置与点击

- **位置**：按钮不再塞进「章节 / 转写文稿」的横向滚动条，而是紧贴在滚动条下方单独一行。滚动条里窄面板会把按钮裁掉、把键盘焦点环切成半圈弧线；它还用拖动来滚动，可能截走点击。
- **点击**：按下时不让事件冒泡到滚动条，并在抬起时直接触发动作（紧随其后的 click 去重），所以滚动条抢占指针也不影响；鼠标不再显示焦点环，只有键盘 Tab 才显示且画在按钮内侧。
- **失效提示**：扩展刚更新过、页面还是旧的脚本时，点「沉浸学习」会提示「请刷新此页面」，而不是毫无反应。

### 转写条（取代入口卡片和面板里的按钮）

参考 YouTube Summary 之类的助手：视频页右栏最上方一条常驻的横条，**不依赖转写面板，也不需要点插件图标**。

```
[书本标] 乔木 · 沉浸学习 ●        [字幕] [复制] [下载] [沉浸学习] [设置] [⌄]
```

- **五个按钮**：字幕（展开并加载字幕列表）、复制、下载、沉浸学习、设置（打开扩展设置 → 常规）；最右的箭头或点击横条本身展开 / 收起下拉，展开状态记在本页的 localStorage。
- **下拉**：状态行（正在读取字幕… / 字幕已就绪，点击时间可跳转 / 没有读到字幕 + 重试按钮）加字幕列表。列表按段落合并，点时间让当前视频跳到该处；最多显示 400 段，更多请进沉浸学习。
- **状态点**：橙色闪烁 = 准备中，绿色 = 已就绪，灰色 = 还没取到。
- **字幕来源**：预取、YouTube 自己渲染的转写面板（自动展开后读取），两者谁先有用谁；复制、下载、展开字幕都会等到有字幕或超时才给结果。
- **失效处理**：页面是扩展更新前打开的，点沉浸学习会提示刷新；按下事件不传给页面，抬起即触发，避免被 YouTube 的拖动滚动吞掉点击。
- 设置里「YouTube 转写文稿按钮」控制这条是否显示，「自动展开 YouTube 转写文稿」控制是否自动展开面板。原先在面板标签栏旁的三枚按钮和独立的入口卡片已删除，避免重复。

### YouTube 自带的转写面板（右栏「在此视频中」）

那是 YouTube 自己的面板，不是我们做的。我们只在「自动展开」时帮你点开它——为了让 YouTube 把字幕行渲染出来作为兜底字幕来源。现在有了转写条，这个面板是重复的，所以：

- **自动展开后把它隐藏**（设置里「隐藏 YouTube 自带的转写面板」，默认开）：用 `display:none` 藏起来而不是关掉，字幕行仍在页面里，转写条、复制、下载和学习模式照常读取。等字幕行渲染好（最多 6 秒）才隐藏，不会饿死兜底。
- **只藏我们打开的**：给它打上 `data-qiaomu-auto` 标记才会隐藏；你自己点「显示转写文稿」打开的面板永远不隐藏，关掉之后标记也会清掉。
- 不想要自动展开：关掉「自动展开 YouTube 转写文稿」即可，此时转写条里的字幕靠预取或首次点击时再读取。

### 转写条的搜索、跟随高亮与点击跳转

参考阅读模式（`reader-transcript.ts`）的做法，并对照常见的字幕 / 歌词跟随体验：

- **点击跳转**：点任意一段，视频立刻跳到该处，并马上把它标成当前行、恢复跟随。
- **跟随高亮**：监听页面里视频的 `timeupdate` / `seeked` / `playing`（捕获阶段监听，视频元素被 YouTube 替换也不丢），二分查找当前行，只在行变化时更新。当前行有蓝色竖条和底色、字重加粗。贴片广告在同一个 video 元素上播放，播放广告时忽略。
- **滚动策略**：默认跟随。当前行仍在列表中间区域（15%–70%）时不动，离开后平滑滚到约三分之一高度处；已经就位不重复滚动；尊重系统「减少动态效果」。
- **让位给用户**：在列表里滚轮、触摸、按下滚动条后暂停跟随 2.5 秒（与阅读模式的 2 秒冷却同一思路）。当前行不在可视区时出现「回到当前位置」按钮；搜索时不自动滚动。
- **跟随开关**：搜索框右侧的定位按钮，开关状态记在本页的 localStorage。
- **搜索**：输入即过滤（停顿 100 ms），匹配词高亮、显示条数、「无结果」提示；清除按钮或 Esc 恢复，并回到当前行。大小写不敏感，中文直接子串匹配。搜索框拦截 keydown / keyup / keypress，避免 YouTube 的单键快捷键（空格、k、f…）在输入时触发。
- **首次展开**：直接定位到正在播放的那一行，而不是列表顶部。
- 上限 1500 段，超出的请进沉浸学习查看。沉浸学习页自身的字幕（阅读模式）原本就支持跟随和点击跳转，搜索目前只在转写条里。

### 学习页字幕的搜索

沉浸学习页的字幕（阅读模式）原本就有跟随高亮和点击跳转，现在加了搜索：字幕上方一条平实的搜索框（只有一条细底线，没有背景和卡片），输入即过滤（停顿 100 ms），章节标题在其下没有匹配行时一并隐藏，右侧显示条数，`×` 或 Esc 清除。匹配词用 CSS Custom Highlight API 标出（与播放高亮同一种机制），不改写文字节点，双语译文也能搜到；时间戳不参与搜索。搜索期间不自动滚动，清除后恢复。

### 当前行的样式（不要用卡片加左侧竖条）

转写条里当前行只靠字体区分：当前行全对比度、字重加粗，时间加粗；其余行字色退一档（搜索时不退），不用底色、不用侧边竖条、没有圆角。圆角底色加蓝色竖条是最典型的「AI 味」样式，已被明确否决。

### 读不到字幕的真正原因（实测）

在真实的已登录 YouTube 页面里逐项核对后发现，自动展开一直没生效，原因有两个，都与界面语言有关：

1. **按钮名按语言变**：描述区里的「显示转写文稿」按钮，中文界面叫「内容转文字」，而我们按「转写」等词去找，找不到。现在按结构找（`ytd-video-description-transcript-section-renderer` 里的按钮），文字匹配只作后备，并覆盖多种语言。
2. **按钮要描述展开才存在**：描述折叠时那一节是空的。现在先展开描述，点开转写后再收回去，页面回到原来的样子；最多尝试展开两次，避免来回折腾。
3. 之前还会误点一个藏在「未展开面板」标题里的同名隐藏按钮，点了没有任何效果；现在凡是在未展开的面板里的按钮都不点。

另外：未登录或被判定为机器人的会话里，YouTube 自己的 `get_transcript` 请求也会被拒绝（带上登录凭据也一样，面板一直转圈），这种情况下哪种方式都读不到，和我们的实现无关。

转写条的行为：预取被拒绝后，**自动**去读 YouTube 自己的转写面板（不再等你点击）；仍然读不到才显示「没有读到字幕」和「重试」，重试会重新展开描述、重新读取。

### 字幕读取方案：对齐成熟开源实现（取代 get_transcript 预取）

调研 youtube-transcript-api（jdepoix）、yt-dlp、Defuddle 的做法，共同点是：**用 InnerTube 的 `/youtubei/v1/player` 以移动端客户端取字幕轨道列表，再下载轨道**。移动端客户端（ANDROID、ANDROID_VR、IOS）不受网页端播放器令牌（PO token）限制；网页端的 `get_transcript` 与 `timedtext` 才需要令牌。我们之前预取走的恰恰是被令牌卡住的 `get_transcript`，所以才在 `Precondition check failed` 上白白失败。

现在的链（在 YouTube 标签页里执行，带你的 cookie 与来源，`youtube-captions.ts`）：

1. 依次请求 `player`：ANDROID（20.10.38）→ ANDROID_VR → IOS，拿到 `captionTracks` 就停。
2. 都被拒绝时，从 `/watch?v=` 页面 HTML 里取内嵌的 `ytInitialPlayerResponse`。
3. 选轨道：口语语言优先——与自动字幕同语种的人工字幕 → 自动字幕 → 任一人工字幕；URL 带 `exp=xpe`（需要令牌）的轨道跳过（与 youtube-transcript-api 抛 `PoTokenRequired` 的条件相同）。
4. 下载：先要 `fmt=json3`，不行再用默认 XML；三种格式（json3、经典 `<text>`、srv3 `<p>`）都能解析并解码实体。
5. 以上都读不到，才进入「展开描述 → 点开 YouTube 自带转写面板 → 读取字幕行」的 DOM 兜底。

本机测试环境被 YouTube 判定为机器人（所有移动端客户端都返回「请登录以确认你不是机器人」），所以这条链没能在真实页面上走通，只用单元测试验证了请求顺序、选轨与解析。

参考：[youtube-transcript-api](https://github.com/jdepoix/youtube-transcript-api)、[YouTube.js](https://github.com/LuanRT/YouTube.js)。

### 转写条滚动交互的修正

- **点一行不再让列表跳**：被点的那行本来就在屏幕上，只标成当前行并让视频跳转，列表原地不动（之前会立刻把它拽到三分之一处，鼠标下的内容跟着跑）。
- **忽略跳转后的旧时间**：跳转后视频会短暂继续上报旧位置，导致高亮闪回；点击后 0.9 秒内忽略，收到 `seeked`（真正跳完）立即恢复。
- **不重复启动滚动**：目标行已在平滑滚动途中时不再发起新滚动（之前每次 timeupdate 都会重启，造成抖动）；很远的跳转直接落位而不是平滑扫过几百行。
- **鼠标停在列表上不动**：指针在列表上时暂停跟随，离开后等 2.5 秒再恢复。

### 为什么明明页面上有字幕行，转写条却说「没有读到」（已修）

用户截图里 YouTube 自己的面板已经把字幕行渲染出来了（带「时间轴 / 章节 / 转写文稿」三个标签），而转写条仍显示「没有读到字幕」。原因是我们只在 `target-id="engagement-panel-searchable-transcript"` 这个面板里找字幕行，而新版布局把转写放在另一个面板（`PAmodern_transcript_view`）里——字幕行就在页面上，我们却看错了地方。

现在不再依赖面板 id：

- **按内容找**：页面上任何位置的 `transcript-segment-view-model` / `ytd-transcript-segment-renderer` 都算字幕行；面板是「装着这些行的那个面板」，找不到再退回已知 id。
- **行元素改名也不怕**：行元素找不到时，改用它的时间戳单元格（class 含 `TranscriptSegmentViewModelTimestamp`）反推所在行。
- **只要页面上出现字幕行，转写条就自动填上**（哪怕是你自己手动展开的面板），不用点任何东西；章节标题、搜索框不会被当成字幕。
- **三个标签**（时间轴 / 章节 / 转写文稿）时，面板停在别的标签就自动切到「转写文稿」。
- **自动展开后的隐藏**也改为作用在「装着字幕行的面板」上，不再只认旧 id。
- 真读不到时提示「没有读到字幕。可以试试在 YouTube 里展开“转写文稿”。」——手动展开后转写条会自动读取。

### 字幕里的「1分钟43秒钟」是什么，以及对齐 YouTube 自己的转写样式

**那些中文时间是什么**：YouTube 在每一行里放了一份给读屏软件用的「口述时间」（`...TimestampA11yLabel`，视觉上隐藏），而且粒度比行更细——一行里每个短句的开头都有一个。我们之前把它当正文读进来，所以字幕里夹着「1分钟43秒钟」。现在：

- 视觉上隐藏的元素（类名含 a11y / sr-only / visually-hidden，或 1px 裁剪、display:none）不再算正文。
- 这些口述时间被当作**更细的时间点**：连同单位词一起解析（`1分钟43秒钟`、`1分43秒`、`1 minute, 43 seconds`、`1時間2分3秒` 等，其他语言解析不了就忽略），每遇到一个就开一条新的、更短的行，点击跳转更准。

**样式和交互按 YouTube 的转写文稿来**：

- 一条字幕一行（几秒一条），不再合并成 30 秒的大段；时间是行首的小圆角标签，不再是蓝字。
- 章节标题（「第 2 章：The necessity of profit」）作为加粗小标题夹在行之间；复制 / 下载里是 `## 标题`，沉浸学习页里是 `<h3>`，搜索时没有匹配行的章节标题一并隐藏。
- 当前行是铺满整行的平整浅灰底、字重加粗，没有圆角、没有左侧竖条；其余行字色退一档。
- 字幕已就绪时不再显示状态行；列表更高（最多视口的 60%）、行铺满宽度。
- 点击一行跳转，搜索、跟随与之前一致。

**自由滑动，10 秒无操作后回到当前**：字幕列表（转写条和沉浸学习页）随时可以自由滚动，任何一次滚轮、触摸或按下都会暂停跟随并重新计时；**连续 10 秒没有操作**，自动平滑回到正在播放的那一行（不必等下一句开始）。关掉跟随开关则不会回去。

### 自由滑动与回到跟随：按业界做法重做

调研了同类实现（[mux-transcript-widget](https://github.com/computershawn/mux-transcript-widget/pull/9)、[youtube-lyrics-pip](https://github.com/fajarbc/youtube-lyrics-pip/pull/2)、foo_openlyrics 等），共识是：

1. **用户意图事件暂停跟随**：wheel、touchmove、按下滚动条、翻页类按键；
2. **最后一次操作之后**才开始倒计时，每次新操作都重新计时（而不是从第一次操作算起）；
3. **区分程序滚动与用户滚动**，否则自己的滚动会把自己暂停，或者用户的滚动被当成自己的；
4. 暂停期间给一个「回到当前位置」按钮，点了立即恢复；用户主动点某一行/拖动进度也恢复跟随。

我们之前的问题：只监听 wheel / touchstart / pointerdown / keydown——拖动滚动条、触控板惯性、触摸滑动、键盘翻页这些「没有新事件」的滚动都不会续期，倒计时从按下那一刻算起，用户还在拖就被拉回去；同时用「1 秒内的滚动都算程序滚动」来区分，自动滚动之后紧接着的用户滚动会被当作程序滚动而无法暂停（约每 6 秒一次自动滚动，就有六分之一的概率）。

现在：

- 程序滚动记下它覆盖的区间（起点→目标）和时间，滚动事件落在这段区间内且在进行中才算「自己的」；其余任何滚动事件（滚动条拖动、惯性、触摸、键盘）都算用户的，并重新计时。
- 意图事件：wheel、touchstart、touchmove、pointerdown、方向键 / 翻页键 / Home / End / 空格；在列表上的其他按键不算。
- 最后一次操作后连续 10 秒无动静，自动回到正在播放的那一行；超过两个屏幕的距离直接落位，不再平滑扫过。
- 打开下拉时我们自己把列表放到当前行，不会被当成用户操作而暂停。
- 在真实 Chrome 里用脚本模拟了「播放 → 用户滚走 → 再次操作 → 空闲 → 回到当前行」的时间线，暂停和 10 秒后的回归与预期一致（无头模式不跑平滑滚动动画和滚动事件，这两项靠单元测试覆盖）。

### 点击不跳、拖动不稳、刷新后没字幕：根因与修复

三个现象其实是同一个根因加两个独立问题：

1. **列表在不停地被重建（根因）**。转写条每次收到页面变化都会 `setState`，而 `setState` 无条件重新渲染整个字幕列表；列表重建本身又是 DOM 变化，反过来触发页面观察器，于是列表以接近每帧一次的频率被销毁重建。后果：鼠标按下和抬起之间那一行已经换了新元素，点击永远落不到（所以点击不跳）；滚动位置被不停重置（所以自由拖动不对）；还白白耗 CPU。修复：`setState` 只在状态或字幕真的变了才动 DOM（相同字幕、相同内容的副本都算没变）；页面观察器忽略发生在转写条内部的变化；文本只在不同时才写。
2. **点击跳转改走页面播放器自己的接口**。内容脚本改 `video.currentTime` 不如播放器 `seekTo` 可靠（播放器的控件、缓冲和状态要跟着走），而播放器对象在页面的 JS 环境里，内容脚本够不着，所以由后台用 `scripting` 在页面环境里调用 `movie_player.seekTo(t, true)` 并播放，失败才退回设置 `currentTime`。只接受来自 YouTube 页面、有限数字。
3. **成功读到过的字幕会缓存**（扩展存储，每个视频一份，最近 30 个，空的或超过 800 KB 的不存）。刷新页面、再次打开同一个视频时立即显示，学习页也不用再等。DOM 读取和接口读取的结果都会写入缓存。
4. **刷新后偶尔读不到**：描述区在刷新后构建得更晚，之前展开描述只试两次、间隔很短，用完了就再也不试。现在每隔约 2.5 秒试一次、最多 8 次，换视频时重新计数；加上缓存，第二次打开基本不依赖 YouTube 的界面。
5. **逐句高亮**：当前行里正在说的那一小句（按标点分句，按距下一行的时间估算位置）用 CSS Custom Highlight API 标出，和沉浸学习页同一机制，不改写文字；搜索时、下拉收起时清除。
